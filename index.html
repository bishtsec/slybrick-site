01Pentesting

We come at it the way an attacker would.

Hand testing against something that ships. No scanner run dressed up as a report — every finding arrives as a request, a response, and what the attacker walks away with.

  • Web

    Web application testing

    Login and session handling, who is allowed to see what, the business rules underneath, and anywhere user input reaches an interpreter.

    Talk to us about web testing

  • API

    API security testing

    REST, GraphQL and gRPC. Object-level access control, fields the client was never meant to set, rate limits, and data that comes back to the wrong caller.

    Talk to us about APIs

  • Mobile

    Mobile application testing

    Android and iOS. Exported components and IPC, secrets shipped inside the binary, and the checks a client trusts the server to make and the server never does.

    Talk to us about mobile

Testing happens only under a signed scope and authorization. Nothing destructive, nothing denial-of-service, nothing out of scope.

02Defense auditing

We read the controls, then check the fix held.

The other half of the job: not where it breaks, but whether the thing meant to stop it is actually in the path. Source first, then the fix, then every path beside the fix.

  • Source review

    Source code review

    Reading the code for the decisions a scanner cannot see — trust boundaries, deserialization, crypto use, and access checks that run too late to matter.

    Talk to us about review

  • Retest

    Retests after a fix

    A fix that closes one path often leaves its siblings open. After the fix ships we check the fix and every neighbouring path, so the class is closed and not the instance.

    Talk to us about a retest

How an engagement runs

  • Stage 1 · Scope and authorization

    We agree what is in play, in writing. No testing without a signed scope.

  • Stage 2 · Manual testing

    Hand testing against auth, access control, business logic and injection.

  • Stage 3 · Proof and escalation

    Every finding gets a working proof, then is pushed to its real worst case before it is written up.

  • Stage 4 · Report and retest

    Reproduction steps, impact, and a fix to aim at. We retest once you have shipped it.

About

Who runs Slybrick.

Slybrick is run by Aditya Bisht, an offensive security researcher based in India (IST, UTC+5:30).

He works authorization boundaries — BOLA/IDOR and cross-tenant isolation — sanitizer-bypass stored XSS, and the protocol seams where two components disagree about identity. He also ships production software, which is where most of the attack intuition comes from.

  • How we operate

    Authorized programs only. No out-of-scope testing, and no destructive or denial-of-service traffic.

  • On real data

    The moment real personal data appears, we stop, record it, and report — never copy it, never publish it.
